An engineering notebook about how to build tool-using agents that remain understandable, bounded and testable. These are design explorations—not claims of scientific breakthroughs.

HYPOTHESIS / 001

Routing is a control problem

An agent should select the simplest tool capable of satisfying a request. Explicit routing is a useful baseline because its behavior is inspectable.

request → classify → select(tool) → execute → verify

Implemented: Explicit prefix routing in Python ToolPilot. Unimplemented: Semantic LLM routing and tool-selection benchmarks.

DESIGN PRINCIPLE / 002

Capability requires boundaries

A tool interface is also a security boundary. Constrain inputs, disallow arbitrary code execution, and return errors as data rather than hiding failures.

allowed_actions ∩ validated_inputs → bounded_execution

Implemented: AST-based arithmetic restrictions, bounded inputs, and no shell execution. Future: Human approval gates for sensitive operations.

EXPERIMENT / 003

Make decisions legible

A trace should reveal which tool was selected, whether it succeeded, and what was returned. Transparency makes debugging and evaluation easier.

trace = [input, selection, result, status]

Implemented: Structured execution traces in ToolPilot. Future: Real measurements of accuracy, latency and failure rates.
